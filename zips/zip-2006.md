# Terminology

The key word "MUST" in this document is to be interpreted as described in
BCP 14 [^BCP14] when, and only when, it appears in all capitals.

The character § is used when referring to sections of the Zcash Protocol
Specification. [^protocol]

The terms "Orchard protocol", "*Orchard pool*", "*Ironwood pool*", and
"version 6 transaction" are to be interpreted as described in ZIP 229.
[^zip-0229]

"NU6.3" is the network upgrade deployed by ZIP 258. [^zip-0258]

An "*Orchard-pool* Action" is an Action description in the Orchard component
of a version 5 or version 6 transaction. An "*Ironwood-pool* Action" is an
Action description in the Ironwood component of a version 6 transaction.


# Abstract

From NU6.3, the primary input of the Orchard Action statement has an
additional component, $\mathsf{disableCrossAddress}$. When it is 1, the output
note of the Action must have the same expanded receiver as the note that the
Action spends. Every *Orchard-pool* Action from NU6.3 onward is restricted in
this way, in version 5 as well as version 6 transactions. For *Ironwood-pool*
Actions the restriction is selected by the `enableCrossAddress` flag of the
Ironwood component.


# Motivation

NU6.3 introduces the *Ironwood pool* so that funds can be migrated out of the
*Orchard pool* after the Orchard soundness vulnerability described in ZIP 257.
[^zip-0229] [^zip-0257] ZIP 258 prevents new value from entering the
*Orchard pool*. [^zip-0258] This ZIP additionally prevents an *Orchard-pool*
Action from sending value to a different recipient, so that transfers between
users create notes in the *Ironwood pool*. This discourages economic activity
between users within the *Orchard pool*, and encourages faster migration to the
*Ironwood pool*. [^zip-0229]


# Specification

## Expanded receivers

The expanded receiver of an Orchard shielded payment address with diversifier
$\mathsf{d}$ and diversified transmission key $\mathsf{pk_d}$ is the pair
$(\mathsf{g_d}, \mathsf{pk_d})$, where
$\mathsf{g_d} = \mathsf{DiversifyHash^{Orchard}}(\mathsf{d})$ is its
diversified base, as defined in § 4.2.3 ‘Orchard Key Components’.
[^protocol-orchardkeycomponents]

The expanded receiver of an Orchard-protocol note is the expanded receiver of
the shielded payment address to which the note is sent, that is, the pair
$(\mathsf{g_d}, \mathsf{pk_d})$ to which its note commitment commits (§ 3.2
‘Shielded Pools and Notes’). [^protocol-notes]

## The `enableCrossAddress` flag

Each Orchard-protocol Action description has a flag
$\mathsf{enableCrossAddress} \in \{0, 1\}$, determined as follows:

* For an Action in a block before NU6.3 activation (necessarily an
  *Orchard-pool* Action), $\mathsf{enableCrossAddress} = 1$.
* For an *Orchard-pool* Action in a block at or after NU6.3 activation,
  $\mathsf{enableCrossAddress} = 0$. This applies to version 5 and version 6
  transactions. Bit 2 of `flagsOrchard` remains a reserved bit that is
  required to be 0 (§ 7.1.2 ‘Transaction Consensus Rules’
  [^protocol-txnconsensus]; ZIP 229 [^zip-0229]); it does not encode
  $\mathsf{enableCrossAddress}$.
* For an *Ironwood-pool* Action, $\mathsf{enableCrossAddress}$ is bit 2 of the
  `flagsIronwood` field of the transaction, as specified in ZIP 229.
  [^zip-0229] It is therefore the same for all *Ironwood-pool* Actions of a
  transaction.

Define $\mathsf{disableCrossAddress} := 1 - \mathsf{enableCrossAddress}$.

## Changes to the Action statement

From NU6.3, the Action statement of § 4.18.4 ‘Action Statement (Orchard)’
[^protocol-actionstatement] is changed as follows:

* The primary input has a final component
  $\mathsf{disableCrossAddress} \in \{0, 1\}$, after $\mathsf{enableOutputs}$.

* The following condition is added:

  **Cross-address restriction**: $\mathsf{disableCrossAddress} = 0$ or
  $(\mathsf{g_d^{old}}, \mathsf{pk_d^{old}}) = (\mathsf{g_d^{new}}, \mathsf{pk_d^{new}})$.

  Here $\mathsf{g_d^{old}}$, $\mathsf{pk_d^{old}}$, $\mathsf{g_d^{new}}$, and
  $\mathsf{pk_d^{new}}$ are the auxiliary inputs of the Action statement, so
  the condition requires the output note to have the same expanded receiver as
  the spent note. The condition does not depend on $\mathsf{v^{old}}$ or
  $\mathsf{v^{new}}$: it applies also when the spent note or the output note
  has value 0.

* The primary input is encoded as a sequence of 10 elements of
  $\mathbb{F}_{q_{\mathbb{P}}}$: the 9 elements of the existing encoding,
  followed by $\mathsf{disableCrossAddress} \pmod{q_{\mathbb{P}}}$.

The Action circuit for this statement is identified as
`OrchardCircuitVersion::PostNU6_3`. It is the corrected circuit deployed in
NU6.2 [^zip-0257], identified as `OrchardCircuitVersion::FixedPostNU6_2` in
§ 4.6 ‘Action Descriptions’ [^protocol-actiondesc], with additional
constraints that enforce the Cross-address restriction condition.

The Action statement for blocks before NU6.3 activation is unchanged.

## Consensus rules

In § 4.6 ‘Action Descriptions’ [^protocol-actiondesc], from NU6.3 the following
rule replaces the rule on proof validity, for each *Orchard-pool* Action and
each *Ironwood-pool* Action:

> [NU6.3 onward] The proof MUST be valid for the verifying key identified by
> `OrchardCircuitVersion::PostNU6_3`, given the primary input
> $(\mathsf{rt}, \mathsf{cv^{net}}, \mathsf{nf^{old}}, \mathsf{rk}, \mathsf{cm}_x, \mathsf{enableSpends}, \mathsf{enableOutputs}, \mathsf{disableCrossAddress})$,
> where $\mathsf{rt}$ is the anchor of the pool to which the Action belongs.

Consequences of this restriction for wallets are described in ZIP 318
[^zip-0318] and ZIP 326. [^zip-0326]


# Rationale

## Encoding of the flag

The transaction encodes $\mathsf{enableCrossAddress}$ in the enabled sense, as
explained in ZIP 229. [^zip-0229] The primary input of the proof uses the
disabled sense. Since Halo 2 instance columns are zero-padded, the 10-element
encoding with $\mathsf{disableCrossAddress} = 0$ commits to the same instance
as the 9-element encoding used before NU6.3.

## Security considerations

The verifying keys of the Action circuits used before NU6.3 do not constrain
the tenth element of the primary input encoding. A proof attests to the
Cross-address restriction only when it is verified with the verifying key
identified by `OrchardCircuitVersion::PostNU6_3`, which the consensus rule
above requires for every Orchard-protocol Action from NU6.3 onward.
