The terms "network upgrade" and "consensus branch" are to be interpreted as described in
ZIP 200 [#zip-0200]_.


Abstract
========

This ZIP specifies a consensus rule that sets an expiry height after which a transaction
cannot be mined. If it is not mined by that height, the transaction will be removed from
nodes' mempools.


Motivation
==========

Transactions that have insufficient fees are often not mined. This indeterminism is a
source of confusion for users and wallets. Allowing a transaction to set a block height
after which it cannot be mined would provide certainty around how long a transaction has
to confirm before it is rejected by the network and must be re-sent.

Advantages include optimizing mempool performance by removing transactions that will not
be mined, and potentially simplifying bidirectional payment channels by reducing the need
to store and compress revocations for past states, since transactions not committed to the
chain could expire and become invalid after a period of time.

If the expiry is at block height $N\!$, then the transaction must be included in block
$N$ or earlier. Block $N+1$ will be too late, and the transaction will be
removed from the mempool.

The new consensus rule will enforce that the transaction will not be considered valid if
included in block of height greater than $N\!$, and blocks that include expired
transactions will not be considered valid.


Specification
=============

Transactions will have a new field, ``nExpiryHeight``, which will set the block height
after which they cannot be mined.

The data type for ``nExpiryHeight`` will be ``uint32_t``. ``nExpiryHeight`` will never
be a UNIX timestamp, unlike ``nLockTime`` values, and thus the maximum expiry height
will be 499999999 (but see the exception for coinbase transactions described in
`Changes for NU5`_).

The following consensus rules apply from Overwinter activation [#zip-0201]_, as also stated
in Section 7.1.2 of the protocol specification [#protocol-txnconsensus]_:

* ``nExpiryHeight`` MUST be less than or equal to 499999999 (from NU5 activation, for
  non-coinbase transactions only).
* If a transaction is not a coinbase transaction and its ``nExpiryHeight`` field is
  nonzero, then it MUST NOT be mined at a block height greater than its ``nExpiryHeight``.

Removal of expired transactions from the mempool, described below, is non-consensus node
behavior.

Note: a previous version of this ZIP incorrectly specified an interaction between
``nExpiryHeight`` and ``nLockTime`` that was never implemented.

For the example below, the last block that the transaction below could possibly be
included in is 3539. After that, it will be removed from the mempool.

::

    "txid": "17561b98cc77cd5a984bb959203e073b5f33cf14cbce90eb32b95ae2c796723f",
    "version": 3,
    "locktime": 2089,
    "expiryheight": 3539,

Default: (Before Blossom) 20 blocks after the height of the next block to be mined (the
chain tip height plus one), or about 50 minutes at 2.5-minute target block spacing. A
configuration option can be used to set the user's default.

Minimum: No minimum

Maximum: 499999999. The wall-clock time corresponding to this absolute height
depends on the block target spacing in effect before it is reached.

No limit: To set no limit on transactions (so that they do not expire), ``nExpiryHeight``
should be set to 0.

Coinbase: ``nExpiryHeight`` on coinbase transactions is ignored, and is set to 0 by
convention.

Every time a transaction expires and should be removed from the mempool, so should all
of its dependent transactions.

Changes for Blossom
-------------------

On Blossom activation [#zip-0206]_, ZIP 208 [#zip-0208]_ recommends that ``zcashd`` RPC
calls that create transactions change the default to 40 blocks after the height of the
next block to be mined, which still represents about 50 minutes at the revised 75-second
target block spacing.

Changes for NU5
---------------

As mentioned above, ``nExpiryHeight`` is ignored for coinbase transactions. However, from
NU5 activation [#zip-0252]_, the ``nExpiryHeight`` field of a coinbase transaction MUST
be set equal to the block height. Also, for coinbase transactions only, the bound of
499999999 on ``nExpiryHeight`` is removed. The motivation is to ensure that transaction
IDs remain unique, as explained in more detail in a note in Section 7.1.2 of the protocol
specification [#protocol-txnconsensus]_.

Changes for NU7
---------------

From NU7 activation [#zip-0259]_, ZIP 218 [#zip-0218]_ recommends that implementations
creating transactions change the default expiry delta from 40 to 120 blocks after the
height of the next block to be mined, which remains approximately 50 minutes at the
25-second target spacing. An explicitly configured expiry delta, such as a
``-txexpirydelta`` value, continues to apply before and after activation. This changes
neither the expiry consensus rule nor the maximum expiry height above.

Expiry across network upgrades
------------------------------

Transaction signatures commit to a consensus branch ID [#zip-0143]_ [#zip-0243]_
[#zip-0244]_ [#zip-0229]_, and from NU5 activation, version 5 and later transactions also
have an ``nConsensusBranchId`` field [#zip-0225]_ that MUST match the consensus branch ID
used for signature hashing [#protocol-txnconsensus]_. A transaction bound in either way to
the consensus branch preceding a network upgrade is therefore not valid in a block at or
above that upgrade's ``ACTIVATION_HEIGHT`` [#zip-0200]_, whatever its ``nExpiryHeight``.

When the ``ACTIVATION_HEIGHT`` of the next network upgrade is known, a wallet creating a
transaction for the current consensus branch SHOULD set its ``nExpiryHeight`` to at most
``ACTIVATION_HEIGHT - 1``.

Nodes might not relay a transaction that will expire within 3 blocks of their view of the
chain tip [#zip-0204]_. A transaction with ``nExpiryHeight`` equal to
``ACTIVATION_HEIGHT - 1`` is in that range when the height of the next block to be mined
is ``ACTIVATION_HEIGHT - 3`` or greater. In that case the wallet SHOULD wait until the
height of the next block to be mined reaches ``ACTIVATION_HEIGHT``, and then create the
transaction for the post-upgrade consensus branch.

A wallet SHOULD treat a transaction that was created for the pre-upgrade consensus branch
and has not been mined as expired once the height of the next block to be mined reaches
``ACTIVATION_HEIGHT``, release its inputs, and notify the user.

Wallet behavior and UI
----------------------

With the addition of this feature, zero-confirmation transactions with an expiration block
height set will have even less guarantee of inclusion. This means that UIs and services
must never rely on zero-confirmation transactions in Zcash.

Wallets SHOULD notify the user of expired transactions that need to be re-sent.

RPC
---

For Overwinter, transaction expiry will be set to a default that can be overridden by the
``-txexpirydelta`` option.

``-txexpirydelta=`` sets the number of blocks, counted from the height of the next block to
be mined, after which a transaction that has not been mined will become invalid.

``zcashd`` (now retired) reported a string ``status`` field, with value ``mined``,
``waiting``, ``expiringsoon``, or ``expired``, for each transaction in the results of
``listtransactions`` and ``gettransaction``.

Config
------

The default will be user-configurable with the option ``-txexpirydelta``; for example,
``-txexpirydelta=100`` on the command line, or ``txexpirydelta=100`` in the config file.

Deployment
----------

This feature was deployed with Overwinter. [#zip-0201]_
