Terminology
===========

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED",
"NOT RECOMMENDED", and "MAY" in this document are to be interpreted as described
in BCP 14 [#BCP14]_ when, and only when, they appear in all capitals.

The terms below are to be interpreted as follows:

Auto-shielding
    The process by which a wallet, without user intervention, transfers transparent
    funds it holds to the most recent shielded pool, not as a direct result of
    receiving a payment (see `Auto-shielding`_).

Auto-migration
    The process by which a wallet, without user intervention, transfers shielded
    funds from older pools to the most preferred (usually the most recent) pool,
    not as a direct result of receiving a payment (see `Auto-migration`_).

Opportunistic migration
    The process of transferring previously received shielded funds from older pools
    to the most preferred (usually the most recent) pool as part of a user-initiated
    transaction.

Transaction output (TXO)
    An output (transparent coin or shielded note) of a transaction on the consensus
    block chain or in the mempool visible to a wallet.

Motivation
==========

Zcash wallets have to serve two purposes as a user agent:

* to manage the economic actions dictated by the user;
* to manage the privacy implications of these actions.

The goal of this ZIP is to document security and privacy best practices when handling
funds and transactions as the user's agent. These best practices are intended to
provide as much privacy as is feasible by default, while still enabling the user's
desired transactions to occur, and exposing any privacy implications to the user so
that they have enough information to assess the consequences of their economic actions.

This ZIP covers best practices for:

* what information to display to the user about transactions and balances;
* how to handle interactions between the ZIP 32 [#zip-0032]_ key tree and
  Unified Addresses [#zip-0316]_;
* when to use external or internal keys/addresses;
* sharing addresses and viewing keys;
* sending and receiving funds (including fee selection);
* migrating funds between pools.

Note: The policies implemented by the legacy `zcashd` internal wallet are known
to be in violation of this ZIP.


Requirements
============

User consent
------------

A wallet typically reveals some information in the process of creating a transaction.
Which information is revealed depends on the configured wallet privacy policy.
The guiding principle of these requirements is that users must explicitly consent
to each instance of information being revealed by the wallet in a transaction.

A user may give blanket consent to reveal a particular kind of information, and
must also be able to change the configured wallet privacy policy to avoid the
wallet creating new information leaks of a given type.

The specifications below describe some situations in which blanket consent may be
inappropriate.

Some varieties of consent may not be revocable, for example if a user chooses to
share some of their keys.


Prompt accessibility of funds
-----------------------------

Wallets need to take account of two main concerns with respect to
accessibility of funds:

* enabling funds to be spent as quickly as possible to reduce latency;
* ensuring that the confirmed-spendable balance is not overestimated,
  and so can be trusted by the user.

These concerns affect the way that balances should be computed, which
notes are selected for spending, and how the wallet should ensure that
sufficient notes are available to cover multiple spends within a short
period.

To support this we define two kinds of TXOs:

* A trusted TXO is a TXO received from a party where the wallet trusts that
  it will remain mined in its original transaction, such as TXOs created by
  the wallet's internal TXO handling, other than the outputs of shielding
  transactions (see `Shielded TXOs`_).
* An untrusted TXO is a TXO received by the wallet that is not trusted.

Wallets can then require that untrusted TXOs need more confirmations before
they become confirmed-spendable than trusted TXOs. This provides an improved
trade-off between latency on the one hand, and reliability and safety on the
other.


Specification
=============

Wallet seeds
------------

To meet the ZIP 32 requirement on the entropy of wallet seeds
[#zip-0032-wallet-seeds]_, when generating a seed byte sequence:

* if using a BIP 39 mnemonic [#bip-0039]_, a 24-word mnemonic will be needed;
* if using SLIP 39 secret sharing [#slip-0039]_, a share length of 33 words will
  be needed.

In the case where a wallet implementation restores a wallet from an existing
mnemonic, it will normally not be in a position to enforce a minimum entropy
requirement on that mnemonic.

A wallet implementation MAY accept BIP 39 mnemonics of fewer than 24 words or
SLIP 39 shares of fewer than 33 words when restoring a wallet (but as specified
above, MUST NOT generate them). If it accepts them —or in other cases where it
can reliably detect that the seed to be restored will have less than 256 bits of
entropy— it SHOULD warn the user that the security of the restored wallet will
be weaker than expected, and SHOULD recommend transferring all of the wallet's
funds, once it has fully synced, to another wallet controlled by the user.


Long-term storage of funds
--------------------------

It is RECOMMENDED that wallets only hold funds as shielded in the long term;
that is, if a wallet supports receiving transparent funds (or supports
importing a seed from another wallet that might have done so), then it SHOULD
auto-shield such funds by default.

A shielding transaction is always linked to the transparent addresses it
spends from. This can cause undesirable information leaks:

a) if the inputs to the transaction are associated with multiple transparent
   addresses, those addresses will be linked to each other;
b) a link between the input transparent address(es) and the payment will be
   visible to the recipient(s), or to any other holder of an Incoming Viewing
   Key for the destination address(es).

Despite the fact that it is not possible to achieve strong privacy guarantees
from *any* use of transparent addresses, it is undesirable to reveal this
additional information. In particular, issue b) motivates ruling out the use
of "opportunistic shielding", i.e. shielding previously received transparent
funds as part of a user-initiated transaction.

Wallets SHOULD NOT shield funds received at multiple transparent addresses
(including transparent receivers) in the same transaction, and SHOULD NOT use
opportunistic shielding.

Following all of the recommendations in this section improves both collective
privacy and the user's individual privacy, by maximizing the size of the note
anonymity set over time and minimizing the potential linkage of shielding
transactions to other transactions.

The remainder of this specification assumes a wallet that follows all of these
recommendations, except where explicitly noted.

Address management
------------------

Zcash wallets SHOULD only use addresses generated deterministically from a
seed as specified in ZIP 32 [#zip-0032]_. The discussion of address management
below assumes this is the case.

The general framework specified in ZIP 32 is that addresses are derived in
a hierarchy [#zip-0032-wallet-usage]_, following a similar structure to that
defined by BIP 44. Each `account` in the derivation path represents a distinct
spending authority. Funds within an account are differentiated according to the
protocol under which the TXOs that contributed to the account balance were
created, but TXOs are not managed individually except when it is required
to select funds from a specific shielded pool in order to reduce information
leakage.

ZIP 316 specifies that when generating a Unified Address, the same diversifier
index MUST be used for each Receiver. [#zip-0316-deriving-a-unified-address]_
This has the consequence that, for wallets that implement address rotation,
care must be taken to avoid accidentally leaking information that allows an
observer to link the ownership of addresses that are intended by the wallet
user to be unrelated to one another.


Allowed transfers
-----------------

Wallets SHOULD NOT spend funds from a transparent address in a transaction with
an external recipient, unless the user gives explicit consent for this on a
per-transaction basis. The user's consent to a ZIP 320 transfer [#zip-0320]_
covers its second transaction, which spends the ephemeral transparent output
of the first. Wallets MAY further restrict the set of transfers they perform.


Auto-shielding
--------------

Auto-shielding requires that the wallet have ambient access to the spending
authority, and that this authority may be exercised without user intervention.
This is not the case for e.g. wallets where key material is stored in a secure
enclave with access that is mediated by direct user interaction, or wallets
used in conjunction with hardware devices.

For wallets that have the required ambient spending authority, auto-shielding
is the process by which transparent UTXOs detected as belonging to the wallet
are shielded by the wallet without user intervention.

Wallet users MUST be able to disable auto-shielding functionality offered by a
wallet.

Auto-shielding is a time-triggered action, not a receipt-triggered action.
An auto-shielding transaction MUST NOT be created as a direct result of a
payment being received. For example, a wallet can sample the time at which
it creates an auto-shielding transaction from a distribution of "time since
last payment to the address", weighted by the balance at that address, so
that as more funds accrue, the auto-shielding transaction becomes more likely.
This ensures that all funds will eventually be auto-shielded, while preventing
fee-dusting attacks (where dust is sent in order to repeatedly consume fees
from the wallet), as the auto-shielding transaction is not directly triggered
by payment receipt.

Automatic shielding and automatic/opportunistic migration SHOULD NOT be
applied to inputs where the cost of shielding or migrating them will
equal or exceed their economic value. If these transactions are paying the
ZIP 317 conventional fee [#zip-0317]_, that will be the case if the
amount of the input to be shielded/migrated is less than or equal to the
marginal fee, and cannot be accommodated by an input that would be present
in any case due to padding of the number of inputs from a given
shielded pool.

Open question: if a wallet is offline for a long time, then it would likely
auto-shield as soon as it finishes syncing. This might not be enough to reveal
that the wallet came online, except that it might result in auto-shielding
transactions for multiple transparent addresses being created at the same time.
Should this case be handled specially?


Trusted and untrusted TXOs
--------------------------

A wallet SHOULD treat received TXOs that are outputs of transactions created
by the same wallet, as trusted TXOs, other than outputs of wallet-internal
shielding transactions, whose spendability is specified separately in
`Shielded TXOs`_. Wallets MAY enable users to mark specific
external transactions as trusted, allowing their received TXOs also to be
classified as trusted TXOs. Wallets MAY also permit users to define alternate
policies for the number of confirmations required before untrusted TXOs may be
spent based on a user-configured value threshold.

A wallet SHOULD have a policy that is clearly communicated to the user for
the number of confirmations needed to spend untrusted and trusted TXOs
(`untrusted_confirmations` and `trusted_confirmations` respectively, with
`trusted_confirmations` ≤ `untrusted_confirmations`). The following
confirmation policy is RECOMMENDED:

* `untrusted_confirmations` = 10, for untrusted TXOs;
* `trusted_confirmations` = 3, for trusted TXOs.

A TXO created in the block at height $h$ has $T - h + 1$ confirmations, where
$T$ is the height of the wallet's view of the chain tip (see
`Categories of TXOs according to spendability`_). An unmined TXO has zero
confirmations.

Wallets SHOULD NOT permit the spending of TXOs with fewer than 3 confirmations,
with the exception of:

* transparent UTXOs that are spent in shielding transactions
* ephemeral transparent UTXOs created in the process of sending funds from
  the shielded pools to a TEX recipient address [#zip-0320]_.

Rationale for the given numbers of confirmations
''''''''''''''''''''''''''''''''''''''''''''''''

The rationale for choosing three confirmations for trusted TXOs is that
anecdotally, reorgs are usually less than three blocks.

The consequences of attempting to spend a trusted TXO may be less severe in the
case of a rollback than the consequences of attempting to spend an untrusted TXO.
The value received from a trusted TXO should always be recoverable, whereas
recovering value received from an untrusted TXO may require the user to request
that funds are re-sent.


Categories of TXOs according to spendability
--------------------------------------------

A TXO is *known-spendable*, relative to a given block chain and wallet
state, if and only if all of the following are true in that state:

* the wallet has not observed the TXO being spent in any block that it has
  scanned, up to and including its view of the chain tip;
* the TXO is not committed to be spent in another unexpired transaction created
  by this wallet; and
* the wallet can effect the spend, either by having access to the TXO's
  spending key (for whatever protocol the TXO uses) or by mediating interaction
  with a hardware device or other offline signing protocol.

The wallet's view of the chain tip is the most recent block of the best chain
that the wallet has learned of from its source of block chain data, whether or
not it has scanned that block. A wallet MAY treat a TXO as known-spendable
before it has scanned every block up to its view of the chain tip. If such a
TXO was in fact spent in a block that the wallet has not yet scanned, then a
transaction that attempts to spend it again will be rejected by the network,
and broadcasting that transaction reveals it (including the nullifiers of any
shielded TXOs it spends) to the parties that receive it.

A TXO is *unconfirmed-spendable*, relative to a given block chain and
wallet state, if and only if the TXO is known-spendable but is not
confirmed-spendable in that state. Confirmed-spendable is defined for
`Shielded TXOs`_ and for `Transparent UTXOs`_ below.

A TXO is *watch-only* if and only if the wallet can detect it (via a full or
incoming viewing key, or via its address in the case of a transparent TXO) but
cannot effect its spend by any means, including via a hardware device or other
offline signing protocol.

A wallet MUST NOT attempt to spend a TXO in a user-initiated transaction
that is not confirmed-spendable. This does not apply to transparent UTXOs spent
in wallet-internal shielding transactions, which need only be
confirmed-shieldable (see `Transparent UTXOs`_), or to the ephemeral
transparent UTXO spent by the second transaction of a ZIP 320 transfer
[#zip-0320]_.

Shielded TXOs
'''''''''''''

A shielded TXO is *confirmed-spendable*, relative to a given block chain and
wallet state, if and only if all of the following are true in that state:

* the TXO is known-spendable; and
* the wallet has sufficient contextual information to be able to effect the
  spend (i.e. it is able to construct required witnesses, etc.); and
* one of the following is true:

  * the TXO is not an output of a wallet-internal shielding transaction, and either:

    * it is trusted and has at least `trusted_confirmations` confirmations; or
    * it is untrusted and has at least `untrusted_confirmations` confirmations.

  * the TXO is the output of a wallet-internal shielding transaction, and both:

    * every transparent UTXO spent in the shielding transaction was produced by
      a transaction that has at least `untrusted_confirmations` confirmations
      (or at least `trusted_confirmations` confirmations, if the user has
      explicitly marked as trusted every transaction that produced such a
      UTXO; see `Trusted and untrusted TXOs`_); and
    * the wallet-internal shielding transaction has at least `trusted_confirmations`
      confirmations.

Transparent UTXOs
'''''''''''''''''

A transparent UTXO is *confirmed-shieldable* relative to a given block chain and
wallet state, if and only if all of the following are true in that state:

* the TXO is known-spendable; and
* the wallet has sufficient contextual information to be able to effect the
  spend (i.e. it is able to construct a correct redeem script, etc.)

A transparent UTXO is *confirmed-spendable*, relative to a given block chain
and wallet state, if and only if all of the following are true in that state:

* auto-shielding is not active;
* the UTXO is confirmed-shieldable; and
* either it is trusted and has at least `trusted_confirmations` confirmations,
  or it is untrusted and has at least `untrusted_confirmations` confirmations.

Wallets MAY attempt to spend received transparent UTXOs in wallet-internal
shielding transactions with zero confirmations. In this case, the resulting
shielded funds are not confirmed-spendable until the conditions given in
`Shielded TXOs`_ hold; they are not trusted merely because they are sent to a
wallet-internal address.

Reporting of balances
---------------------

Wallets SHOULD report:

* Confirmed-spendable balance.
* Pending balance, *or* total balance.

Wallets MAY report:

* Un-economic balance.

These are calculated as follows:

* The confirmed-spendable balance is the sum of values of confirmed-spendable
  TXOs. This balance MAY ignore notes with value less than or equal to the
  ZIP 317 marginal fee [#zip-0317]_.
* The pending balance is the sum of values of unconfirmed-spendable TXOs. This
  balance MAY ignore notes with value less than or equal to the ZIP 317
  marginal fee [#zip-0317]_, and MUST exercise this option in a way that is
  consistent with how the confirmed-spendable balance is computed.
* The total balance is the confirmed-spendable balance plus the pending
  balance.
* The un-economic balance is the total of TXOs that individually have value
  less than or equal to the ZIP 317 marginal fee [#zip-0317]_. Such TXOs can
  only usefully be spent as "grace inputs", as their value does not exceed the
  fee required to spend them; wallets MAY ignore the presence of such notes in
  note selection and balance calculation. If wallets ignore the presence of such
  notes, they MUST do so consistently; i.e. wallets MUST NOT report them as
  part of balance that is exposed to the user as spendable or pending if the
  wallet does not provide any mechanism to spend them.

Note: the definitions of "confirmed-spendable" above ensure that, if
auto-shielding is enabled, transparent funds will be reported in the pending
or total balance, but not in the confirmed-spendable balance. Since a wallet
MAY treat TXOs as known-spendable before it has scanned every block up to its
view of the chain tip, balances computed before that scan completes can
include TXOs that have since been spent.

If auto-shielding is disabled, the wallet MAY report shielded and
transparent balances separately. If it does so, it MUST make clear
whether each reported balance corresponds to a confirmed-spendable,
pending, or total subset of funds.

Rationale for reporting of balances
'''''''''''''''''''''''''''''''''''

If auto-shielding is disabled, then separate shielded and transparent
balances can constitute useful information. If auto-shielding is enabled
then the wallet can and will automatically spend transparent TXOs in
order to shield them, and so transparent TXOs need to be presented as
pending, not as part of the balance spendable by the user.

Potentially, for expert users, separate shielded balances per pool
could also be useful.

Open question: Does the specification of balance reporting give the user
sufficient visibility into the operation of auto-shielding and pool
migration/usage?

Reporting of transactions
-------------------------

If a transaction includes watch-only received TXOs, the total value of its
watch-only received TXOs MUST be reported separately to any potentially
known-spendable balance.

Incoming transactions
'''''''''''''''''''''

A transaction is *received* if the wallet detects in it a TXO paid to one of
the wallet's addresses or viewing keys (including a watch-only TXO), other than
change from a transaction that the wallet created. A received transaction is
*incoming* while it is unmined or any of its received TXOs is
unconfirmed-spendable.

Received transactions SHOULD be reported with their number of confirmations
and their balances as described in `Reporting of balances`_; incoming
transactions SHOULD be marked as pending.

Sent transactions
'''''''''''''''''

A transaction is sent if it was either:

* created by the wallet, or
* detected by using the wallet's outgoing viewing keys to decrypt
  Sapling or Orchard-protocol (Orchard-pool or Ironwood-pool) outputs, or
* detected as spending a note that was at some time held by the
  wallet by recognizing that note's nullifier, or
* detected as spending a transparent TXO associated with one of
  the wallet's addresses (including watch-only addresses).

Sent transactions SHOULD be reported with their number of confirmations,
an estimate of how long until they expire (if they are unmined and
have an expiry height), and their balances as described in
`Reporting of balances`_.

Resubmission and expiry of transactions
'''''''''''''''''''''''''''''''''''''''

A wallet SHOULD resubmit a transaction that it created until the transaction
is mined, expires, or a conflicting transaction (one that spends any of the
same TXOs) is mined, since nodes might not relay it or might evict it from
their mempools [#zip-0401]_. Some nodes do not accept or relay a transaction
that will expire within ``TX_EXPIRING_SOON_THRESHOLD`` blocks of their view of
the chain tip [#zip-0204]_, so resubmission that close to expiry might not be
effective.

A transaction with nonzero ``nExpiryHeight`` $N$ cannot be mined in a block at
height greater than $N$ [#zip-0203]_. A wallet SHOULD treat such a transaction
as expired only once its view of the chain tip is at height $N$ or greater and
the transaction is not mined in that chain. If a rollback then takes the
wallet's view of the chain tip below height $N$ then the transaction is no
longer expired. A transaction with ``nExpiryHeight`` = 0 does not expire.

When a transaction expires, the wallet SHOULD notify the user [#zip-0203]_,
and the TXOs it spent become available to other transactions, subject to
`Note selection`_.


Display of voluntary fund removal
''''''''''''''''''''''''''''''''''

Wallets that support voluntary removal of funds from circulation as specified
in ZIP 233 [#zip-0233]_ SHOULD display clear, user-friendly messaging at
transaction confirmation time explaining the purpose and effect of the removal.

For example, a wallet might display:

    "These funds will be used for network sustainability purposes. They will
    be gradually reissued to support the long-term security of the Zcash
    network."

This guidance applies to user-initiated voluntary removals via ZIP 233. It
does not apply to the automatic removal of transaction fees specified in
ZIP 235 [#zip-0235]_, which occurs without user action and does not require
explicit user confirmation.


Transaction creation
--------------------

Obtaining user consent for information leakage
''''''''''''''''''''''''''''''''''''''''''''''

Information leakage analysis
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The privacy provided by a Zcash transaction depends on the information leaked
in the creation of that transaction and the process of it being broadcast for
inclusion in the block chain.

The requirements in this section are intended to minimize the leakage of such
information where possible, and to ensure that the user is informed of any
remaining information that would be leaked, and consents to such leakage.

The list below describes the kinds of information that might be leaked. After
a candidate transaction has been created and prior to it being revealed
outside a trusted path to the user, the wallet user interface SHOULD obtain
the user's consent for all of the leaked information.

Assumption: There is always a transaction confirmation step for transactions
that send funds out of the wallet.


Kinds of information leakage
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

* Transaction version (v4 or v5 as of NU5; v4, v5 or v6 as of NU6.3; v5 or v6
  as of NU7)

Before NU6.3 activation, it is RECOMMENDED to use v5 transactions unless Sprout
funds are being spent.

From NU6.3 activation, it is RECOMMENDED to use v6 transactions. Ironwood-pool
Actions occur only in v6 transactions [#zip-0229]_, so a transaction that pays
an Orchard receiver (see `Payments to Orchard receivers`_) is necessarily v6.
A v5 transaction MAY be used when a signer supports only v5, for example a
hardware wallet signing an Orchard-to-transparent transaction
[#zip-0229-requirements]_; such a transaction is distinguishable from a v6
transaction. Before NU7 activation, v4 transactions are needed only to spend
Sprout funds; from NU7 activation, v4 transactions are invalid and Sprout funds
cannot be spent [#zip-0259]_ [#zip-2003]_.

* Lock time (rarely used; may be a distinguisher if it is)

SHOULD be zero.

* Expiry height and anchor position

See `Anchor selection`_ below.

These give information about what block height the creator was synced to, and
some policy information.

* Transparent inputs and outputs

See `Linkability of transactions or addresses`_.

* Public value balances

  * Together with the transparent inputs and outputs, these determine the fee
    and the amount being transferred between pools.
  * The fee is dependent on policy, but for a given policy we attempt to make
    it only depend on other already-leaked metadata.

TODO: we SHOULD try to create fully shielded transactions where possible.

* Numbers of JoinSplits, Spends, Outputs, Orchard-pool Actions, and
  Ironwood-pool Actions

  * This could correlate with other information under certain circumstances.
    For example in a “dusting attack”, the adversary sends a victim lots of
    small-valued notes (or notes with strategically chosen values),
    increasing the probability that the victim’s transactions will have a
    larger number of spends than other transactions (or an identifiable
    number of spends). There are note management strategies that can mitigate
    this, but they have not been implemented yet.

* Which spends of given TXOs are repeated across transactions

  * This may happen because a previous transaction expired and the user is
    trying to spend some of the same TXOs.

* Whether the transaction is coinbase

* For coinbase transactions, the amounts / destination addresses / memos of
  shielded outputs

* Orchard-protocol bundle flags (enableSpends/enableOutputs/enableCrossAddress)
  of the Orchard-pool and Ironwood-pool bundles

  * Under normal circumstances enableSpends and enableOutputs only depend on
    whether the transaction is coinbase.
  * From NU6.3 activation, coinbase transactions have no Orchard-pool Actions,
    and enableCrossAddress is 0 in every Orchard-pool bundle [#zip-0258]_.
  * The enableCrossAddress flag SHOULD be 1 in every Ironwood-pool bundle, so
    that transfers to the same address as the notes spent cannot be
    distinguished from payments.


Linkability of transactions or addresses
''''''''''''''''''''''''''''''''''''''''

Motivation for choices reducing linkability
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

We want to support creating unlinkable addresses, in order that a user can
give different addresses to different counterparties, in such a way that the
counterparties (even if they collude) cannot tell that the addresses were
provided by the same or distinct users.

If multiple UTXOs are received at the same transparent address, it is safe
to shield them all in the same transaction, because that is not leaking
additional information.

Shielding UTXOs received at different transparent addresses in the same
transaction would link those addresses, and hence any diversified Unified
Addresses that contain them as transparent receivers; this is ruled out in
`Long-term storage of funds`_. Ideally, when they are shielded in separate
transactions, this should be done in such a way that the timing of those
transactions is not linkable.

than explicitly say in the specification of how to construct transactions
how to mitigate it, then implementors will ignore it.

When spending transparent UTXOs, they SHOULD only be sent to an internal
shielded receiver belonging to the wallet, except when they are generated
and spent ephemerally as part of a ZIP 320 transfer [#zip-0320]_.

A wallet MUST NOT send funds to a transparent address, including a TEX address
[#zip-0320]_, unless all of the funds being sent come from shielded pools, and
these SHOULD come from a single shielded pool. For a ZIP 320 transfer, the
funds being sent are those spent by its first transaction; the second
transaction, which spends the ephemeral transparent output to the TEX address,
conforms if the first does.

We want to minimize pool crossing.

Payments to Orchard receivers
'''''''''''''''''''''''''''''

From NU6.3 activation, a payment to an Orchard receiver MUST be made as an
Ironwood-pool output, which requires a v6 transaction [#zip-0229]_. This
follows from the requirement to use the most preferred Receiver of a Unified
Address that the sender supports [#zip-0316]_, the requirement that a wallet
not send funds to any external receiver in the Orchard pool after NU6.3
activation [#zip-0326]_, and the consensus rules that disable cross-address
transfers within the Orchard pool and prevent value from entering it
[#zip-0258]_.

Anchor selection
''''''''''''''''

Let $H$ be the target height of a transaction, i.e. the height of the block in
which it is expected to be mined. This is normally $T + 1$ where $T$ is the
height of the wallet's view of the chain tip. A wallet SHOULD choose as anchor
the final treestate of the block at height $H$ − `trusted_confirmations`, which
with the RECOMMENDED policy is the block at height $T - 2$ in the normal case.
This makes every trusted TXO with at least `trusted_confirmations`
confirmations spendable.


Rationale for anchor selection
''''''''''''''''''''''''''''''

* If the chain rolls back past the block at which the anchor is chosen, then
  the anchor and the transaction will be invalidated. This is undesirable
  both for reliability, and because the nullifiers of spent shielded notes
  will have been revealed, which could link this transaction to future
  transactions that spend those notes (see `Note selection`_ for the
  mitigation).
* On the other hand, it is undesirable to choose an anchor too many blocks
  back, because that prevents more recently received shielded notes from
  being spent.
* Using a fixed anchor depth (as opposed to a different depth depending on
  whether or not we are spending trusted shielded notes) avoids leaking
  information about whether or not the shielded notes we spent were
  trusted.


Note selection
''''''''''''''

The nullifiers of notes are *revealed* when a transaction that spends them is
broadcast (to the network or to a light wallet server), included in a block,
or otherwise disclosed to another party.

When a transaction created by the wallet is invalidated after it has revealed
the nullifiers of notes (for example, because it expired, or because the chain
rolled back past its anchor), the wallet SHOULD spend those notes in a note
management transaction to an internal receiver, before using them in any other
transaction. This avoids linking the invalidated transaction with some
arbitrary future transaction.

Provided that no transparent output of the invalidated transaction leaves the
wallet's control, the note management transaction SHOULD preserve the numbers
of spends and outputs in each pool, and the transparent outputs, of the
invalidated transaction. This also avoids revealing whether the user changed
their mind about whether to send the original semantic transaction. (Shielded
outputs to other parties can be replaced by outputs of the same value to an
internal receiver without this being detectable.)

If a transparent output of the invalidated transaction leaves the wallet's
control (for example, a payment to a transparent or TEX address), then
re-creating that output would make the payment, which requires the user's
consent. For this purpose, an output to an ephemeral address of a ZIP 320
transfer [#zip-0320]_ leaves the wallet's control, since it exists only to pay
the TEX address. If the user does not consent to making the payment, the
note management transaction SHOULD send the funds to an internal shielded
receiver.


Expiration height
'''''''''''''''''

A wallet SHOULD create a transaction with ``nExpiryHeight`` set to $H$ plus the
default expiry delta, where $H$ is its target height (see `Anchor selection`_).
The default expiry delta is 120 blocks if NU7 is active at height $H$ and
40 blocks otherwise [#zip-0203-nu7]_ [#zip-0218]_. Both are approximately
50 minutes at the target block spacing in effect. If the user has configured an
expiry delta, the wallet SHOULD use the configured value both before and after
NU7 activation.

Network-layer privacy
---------------------

A server or network operator that sees the IP address from which a transaction
is broadcast can correlate that address with the transaction on chain, and so
with any amounts that the transaction reveals (for example, by crossing pools).

* A wallet SHOULD offer to connect to light wallet servers through an
  anonymity network such as Tor. When this is enabled, the wallet SHOULD route
  transaction broadcasts through that network.
* A wallet SHOULD NOT broadcast a transaction over the same connection or
  circuit as a synchronization that may identify the wallet, and SHOULD use a
  separate circuit for each broadcast, so that its transactions cannot be
  linked by their origin. A wallet MAY broadcast to a different server from
  the one it uses for synchronization.
* Before broadcasting a transaction that reveals amounts without network-layer
  privacy, a wallet SHOULD inform the user of this correlation risk.

ZIP 318 imposes stricter requirements for the broadcast of migration
transactions [#zip-0318-network-layer-privacy]_.

Auto-migration
--------------

Auto-migration is a time-triggered action, not a receipt-triggered action.
Receipt of a shielded payment MUST NOT trigger any on-chain behaviour, as that
reveals transaction linkability; in particular, an auto-migration transaction
MUST NOT be created as a direct result of a payment being received.

A wallet MAY also perform opportunistic migration: if it is making a
user-initiated transaction that spends from an older pool anyway, it can
migrate as much as it would in an auto-migration transaction, which saves a
transaction. This is subject to
`Information leakage for transfers between pools`_, and does not apply to
shielding, since opportunistic shielding is ruled out in
`Long-term storage of funds`_.

Migration of funds from the Orchard pool to the Ironwood pool after NU6.3
activation is specified in ZIP 318 [#zip-0318]_.


Information leakage for transfers between pools
-----------------------------------------------

When the funds in a single shielded pool suffice for a transfer, a wallet
SHOULD spend from that pool alone.

A transaction that moves value between shielded pools (including by spending
notes from more than one pool) reveals the amount crossing between those pools
publicly, as opposed to revealing it only to the holder of a viewing key
authorized to see that amount. A wallet MUST NOT create such a transaction
unless the user has consented to revealing that amount, either for that
transaction or through a configured privacy policy that permits revealed
amounts (see `User consent`_). Consent for a single transaction can be
obtained at the transaction confirmation step, provided that the wallet
discloses there that the transaction crosses pools and the amount that will
be revealed. In particular, wallets MUST NOT automatically combine funds
across pools to satisfy a transfer without such consent, since that could
reveal the total funds the user holds in some pool.

The Orchard pool and the Ironwood pool are distinct pools for this purpose
[#zip-0229]_. From NU6.3 activation, cross-address transfers within the Orchard
pool are disabled [#zip-0258]_, so a payment to a shielded address of another
party that is funded from Orchard-pool notes always crosses pools and requires
this consent; see also ZIP 318 [#zip-0318]_.

In order to maintain the integrity of IVK guarantees, wallets should not generate
unified addresses that contain internal receivers, nor expose internal receivers
(such as those used for auto-shielding and change outputs) in any way.

Change outputs
''''''''''''''

Change SHOULD be sent to an internal receiver of the account that funds the
transaction, in a shielded pool that the transaction already spends from or
sends to, in order to avoid an additional pool crossing. From NU6.3 activation,
the following also apply:

* Change MUST NOT be sent to an external receiver in the Orchard pool
  [#zip-0326]_.
* Change can be sent to an internal receiver in the Orchard pool only in an
  Action whose spent note (which can be a dummy note) is at that same
  receiver, and only if the transaction's ``valueBalanceOrchard`` is
  nonnegative [#zip-0258]_.
* Change from a transaction that spends Orchard-pool notes, if it is not sent
  to the Orchard pool as above, SHOULD be sent to the Ironwood pool, even if
  the transaction does not otherwise involve that pool.

Wallet Recovery
---------------

When a wallet is restored from a seed, rather than from a backup of the
wallet's own data, it does not have enough information to determine which
receiver types the user originally used when deriving each Unified Address
under an account. There is a similar issue when a UFVK is exported, an address
is derived from it, and a payment is sent to that address: a wallet holding the
UFVK will detect the payment, but cannot determine which Unified Address it
should display. A wallet could store this information in the memo field of
change outputs, but that adds a bunch of coordination to the problem, and
assumes ongoing on-chain state storage.

- If the receiver matches an address that the wallet knows it derived (for
  example, with receiver types that the user selected), the wallet SHOULD show
  that Unified Address.
- For each release of a wallet, the wallet SHOULD specify a set of receiver
  types and an associated range of block heights during which the wallet
  will, by default, generate Unified Addresses using that set of receiver
  types.
- Subsequent releases of a wallet SHOULD NOT retroactively change their
  policies for previously defined block height ranges.
- If the receiver matches a UFVK in the wallet, and the wallet is looking it
  up because it detected a received note in some block, the wallet SHOULD show
  the Unified Address with the receiver types given by its policy for that
  block height (ideally the earliest block height at which it detects the
  receiver), and cache this for future usage.
- If the receiver type for a note received at a given time is not a member
  of the set of receiver types expected for the range of block heights, the
  policy corresponding to the nearest block height range that includes that
  receiver type SHOULD be used.
- If the receiver matches a UFVK in the wallet, and the wallet has no
  information about when this receiver may have been first used, it SHOULD
  show the Unified Address corresponding to the most recent receiver types
  policy that includes the receiver's type.
- A wallet that restores a seed created by another implementation does not
  know that implementation's policy, and SHOULD apply its own policy as above.
- A wallet SHOULD recognize every Sapling or Orchard receiver derived from a
  UFVK in the wallet, not only the receivers of addresses that it has recorded
  deriving; for example, by decrypting the receiver's diversifier with the
  UFVK's diversifier key to obtain its diversifier index, and checking that
  the receiver is derived from the UFVK at that index. A lookup of recorded
  receivers is then only an optimisation.

From NU6.3 activation, the Orchard receiver at a given diversifier index
depends on the account's `use_qsk` value, which is not known when restoring
from seed; the wallet then scans with both values, as specified in ZIP 326
[#zip-0326-restoring-from-seed]_. Until the wallet has determined `use_qsk` for
the account, the Orchard receiver to show in a reconstructed Unified Address is
undetermined.

Transparent address recovery
''''''''''''''''''''''''''''

Transparent addresses derived from a ZIP 32 seed use the BIP 44 path
``m/44'/coin_type'/account'/scope/index`` [#bip-0044]_, where:

* scope 0 is used for external addresses, including the transparent receivers
  of Unified Addresses, for which the index is the diversifier index
  [#zip-0316-deriving-a-unified-address]_;
* scope 1 is used for internal addresses, such as change
  [#zip-0316-deriving-internal-keys]_;
* scope 2 SHOULD be used for the ephemeral addresses of ZIP 320 transfers
  [#zip-0320]_, so that they can be recovered from the seed and do not collide
  with external or internal addresses.

For each scope, a wallet uses a *gap limit*: the number of consecutive indices,
beyond the highest index that has received funds, at which it will generate
addresses. The gap limit counts BIP 44 child indices, not Unified Addresses; an
index that is skipped because it does not give a valid Sapling diversifier
still counts.

* A wallet SHOULD NOT generate or expose a transparent address at an index that
  is more than the gap limit beyond the highest index in that scope that has
  received funds.
* When recovering from a seed, a wallet SHOULD look for funds at each index in
  each scope, in order, until it finds a run of consecutive indices that have
  not received funds whose length is the gap limit.
* The RECOMMENDED gap limits are 10 for external addresses, 5 for internal
  addresses, and 10 for ephemeral addresses.

A restoring wallet that uses smaller gap limits than the wallet that created
the seed can fail to find transparent funds. Independently of the gap limits,
all wallets MUST assume that there may be transparent funds associated with
diversifier index 0 for each ZIP 32 account
[#zip-0316-deriving-a-unified-address]_.
