Terminology
===========

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" in this document are
to be interpreted as described in BCP 14 [#BCP14]_ when, and only when, they appear in all
capitals.

The terms below are to be interpreted as follows:

Light client
  A client that is not a full participant in the network of Zcash peers. It can send and
  receive payments, but does not store or validate a copy of the block chain.

Abstract
========

This proposal defines a protocol for a Zcash light client supporting shielded transactions
in the Sapling, Orchard, and Ironwood pools.

Motivation
==========

Currently a client that wishes to send or receive shielded payments must be a full node
participating in the Zcash network. This requires an amount of available bandwidth,
space, and processing power that may be unsuitable for some classes of user. This light
client protocol addresses that need, and is appropriate for low-power,
bandwidth-conscious, or otherwise limited machines (such as mobile phones).

High-Level Design
=================

There are three logical components to a Zcash light client system:

- **Zcash node** that provides chain state and serves as a root of trust for the system.

- **Proxy server** that extracts block chain data from a full node to store and serve it in
  a lower-bandwidth format.

- **Light client** that subscribes to the stream from a proxy server and uses that data to
  update its own view of the chain state. The light client MAY be attached to a wallet
  backend that will track particular shielded notes.

Security Model
==============

In this model, we propose **payment detection privacy** as our main security goal. That
is, the proxy should not learn which transactions (received from the block chain) are
addressed to a given light wallet. If we further assume network privacy (via Tor or
similar), the proxy should not be able to link different connections or queries as
deriving from the same wallet.

In particular, the underlying Zcash node / proxy combination is assumed to be "honest but
curious" and is trusted to provide a correct view of the current best chain state and to
faithfully transmit queries and responses. The light client SHOULD connect to the proxy
server using TLS [#RFC8446]_ with authentication of the server, so that a network attacker
can neither impersonate the proxy server nor read or alter the queries and responses.

This ZIP does not address how to spend notes privately.

Compact Stream Format
=====================

A key observation in this protocol is that the encrypted note field (``encCiphertext``) of
each Sapling Output description and each Orchard or Ironwood Action description is several
hundred bytes long, due to the inclusion of a transaction “memo”. The need to download
this entire field imposes a substantial bandwidth cost on each light wallet, which may be
a limited mobile device on a restricted-bandwidth plan. While more efficient techniques
can be developed in the future, for the moment we propose ignoring the memo field during
payment detection. Furthermore, we can also ignore any information that is not directly
relevant to a shielded transaction.

A **compact block** is a packaging of ONLY the data from a block needed to:

1. Detect a payment to your shielded address
2. Detect a spend of your shielded notes
3. Update your witnesses to generate new spend proofs
4. Detect and spend transparent outputs of your wallet, if transparent data is requested

A compact block and its component compact transactions are encoded on the wire using the
following Protocol Buffers [#protocolbuffers]_ format. It is that of
``compact_formats.proto`` in version 0.5.0 of the light wallet protocol definitions
[#lightwallet-protocol]_, with comments abridged:

.. code:: proto

    message CompactBlock {
        reserved 1;                      // was protoVersion
        reserved "protoVersion";
        uint64 height = 2;               // the height of this block
        bytes hash = 3;                  // if present, the hash of this block
        bytes prevHash = 4;              // if present, the hash of the previous block
        uint32 time = 5;                 // if non-zero, Unix time when the block was mined
        bytes header = 6;                // if present, the full block header
        repeated CompactTx vtx = 7;      // compact transactions from this block
        ChainMetadata chainMetadata = 8; // the state of the chain as of this block
    }

    message ChainMetadata {
        uint32 saplingCommitmentTreeSize = 1;  // tree sizes as of the end of this block
        uint32 orchardCommitmentTreeSize = 2;
        uint32 ironwoodCommitmentTreeSize = 3;
    }

    message CompactTx {
        uint64 index = 1;                // the index of the transaction within the block
        bytes txid = 2;                  // the transaction ID
        uint32 fee = 3;                  // the transaction fee, if the server knows it
        repeated CompactSaplingSpend spends = 4;
        repeated CompactSaplingOutput outputs = 5;
        repeated CompactOrchardAction actions = 6;          // Orchard-pool Actions
        repeated CompactOrchardAction ironwoodActions = 9;  // Ironwood-pool Actions
        repeated CompactTxIn vin = 7;    // transparent inputs, omitting the coinbase input
        repeated TxOut vout = 8;         // transparent outputs
    }

    message CompactSaplingSpend {
        bytes nf = 1;                    // [32] nullifier
    }

    message CompactSaplingOutput {
        bytes cmu = 1;                   // [32] u-coordinate of the note commitment
        bytes ephemeralKey = 2;          // [32] ephemeral public key
        bytes ciphertext = 3;            // [52] first 52 bytes of encCiphertext
    }

    message CompactOrchardAction {
        bytes nullifier = 1;             // [32] nullifier of the input note
        bytes cmx = 2;                   // [32] x-coordinate of the note commitment
        bytes ephemeralKey = 3;          // [32] ephemeral public key
        bytes ciphertext = 4;            // [52] first 52 bytes of encCiphertext
    }

    message CompactTxIn {
        bytes prevoutTxid = 1;           // txid of the transaction whose output is spent
        uint32 prevoutIndex = 2;         // index of that output in its vout
    }

    message TxOut {
        uint64 value = 1;                // value in zatoshis
        bytes scriptPubKey = 2;
    }

Encoding Details
----------------

The fields ``hash``, ``prevHash``, ``txid``, and ``prevoutTxid`` are 32-byte values in
protocol byte order (not byte-reversed or hex-encoded): a block hash as it appears in the
``hashPrevBlock`` field of a block header [#protocol-blockheader]_, and a transaction ID as
defined in [#protocol-txnidentifiers]_. The fields ``nf``, ``cmu``, ``nullifier``, ``cmx``,
and ``ephemeralKey`` are encoded as the corresponding fields of a Spend, Output, or Action
description [#protocol-spendencodingandconsensus]_ [#protocol-outputencodingandconsensus]_
[#protocol-actionencodingandconsensus]_. If present, ``header`` is the block header encoded
as in [#protocol-blockheader]_. The coinbase transaction has ``index`` 0. Within a
``CompactTx``, spends, outputs, and Actions are in the order in which they appear in the
transaction.

Outputs, spends, and Actions are compressed as described in the following sections.

Output Compression
------------------

In the normal Zcash protocol, the output ciphertext [#protocol-outputencodingandconsensus]_
consists of the AEAD-encrypted form of a *note plaintext* [#protocol-notept]_:

+----------------+----------+----------+---------------+-----------------------------------+
| 8-bit leadByte | 88-bit d | 64-bit v | 256-bit rseed | memo (512 bytes) + tag (16 bytes) |
+----------------+----------+----------+---------------+-----------------------------------+

The allowed values of ``leadByte`` depend on the pool and the block height
[#protocol-noteptconcept]_. For Sapling it is 0x01 before Canopy, 0x01 or 0x02 during the
ZIP 212 grace period, and 0x02 after it [#zip-0212]_. Orchard notes use 0x02, and
Ironwood notes use 0x03 [#zip-2005]_.

A recipient detects their transactions by trial-decrypting this ciphertext. On a full node
that has the entire block chain, the primary cost is computational. For light clients
however, there is an additional bandwidth cost: every ciphertext on the block chain must
be received from the server (or network node) the light client is connected to. This
results in a total of 580 bytes per output that must be streamed to the client (in addition
to the 32-byte ephemeral public key).

However, we don't need all of that just to detect payments. The first 52 bytes of the
ciphertext contain the contents and opening of the note commitment, which is all of the
data needed to spend the note and to verify that the note is spendable. If we ignore the
memo and the authentication tag, we're left with a 32-byte ephemeral public key, the 32-byte
note commitment, and only the first 52 bytes of the ciphertext for each output needed to
decrypt, verify, and spend a note. This totals to 116 bytes per output, for an 80%
reduction in bandwidth use. The same applies to Orchard and Ironwood Actions, where the
compact form also carries the 32-byte nullifier of the Action's spent note (needed both to
detect spends and to decrypt the output), for a total of 148 bytes per Action.

However, skipping the full ciphertext means that we can no longer calculate the
authentication tag for the entire ciphertext and will need to do something else to
validate the integrity of the decrypted note plaintext.

Since the note commitment is sent outside the ciphertext and is authenticated by the
binding signature over the entire transaction, it serves as an adequate check on the
validity of the decrypted plaintext (assuming you trust the entity assembling
transactions). We therefore recalculate the note commitment from the decrypted plaintext.
If the recalculated commitment matches the one in the output, we accept the note as valid
and spendable.

Spend Compression
-----------------

Recall that in a version 4 transaction, a Sapling Spend description is 384 bytes long
[#protocol-spendencodingandconsensus]_:

+-------+--------------+-----------+
| Bytes | Name         | Type      |
+=======+==============+===========+
| 32    | cv           | char[32]  |
+-------+--------------+-----------+
| 32    | anchor       | char[32]  |
+-------+--------------+-----------+
| 32    | nullifier    | char[32]  |
+-------+--------------+-----------+
| 32    | rk           | char[32]  |
+-------+--------------+-----------+
| 192   | zkproof      | char[192] |
+-------+--------------+-----------+
| 64    | spendAuthSig | char[64]  |
+-------+--------------+-----------+

In version 5 and later transactions, a Spend description is 96 bytes (``cv``,
``nullifier``, and ``rk``). The 192-byte proof and the 64-byte spend authorization signature
are carried in separate arrays, and the anchor is shared by all spends in the transaction
[#zip-0225]_.

The only part necessary for detection is the nullifier, which allows a light client to
detect when one of its own notes has been spent. This means we only need to take 32 bytes
of each Spend, for a 90% improvement in bandwidth use.

Proxy operation
===============

The proxy's purpose is to provide a scalable and bandwidth-efficient interface between a
Zcash node and any number of light clients. It accomplishes this by parsing a blockwise
stream of transactions from the node and converting them into the compact format described
above.

The proxy offers to light clients the ``CompactTxStreamer`` gRPC service defined in
``service.proto`` in version 0.5.0 of the light wallet protocol definitions
[#lightwallet-protocol]_. The light client operations in this ZIP use the following
methods:

``GetLatestBlock(ChainSpec)``
  Returns the ``BlockID`` (``height`` and ``hash``) of the tip of the server's best chain.

``GetBlock(BlockID)``
  Returns the ``CompactBlock`` at the given height, with data for all pools.

``GetBlockRange(BlockRange)``
  Streams the ``CompactBlocks`` from ``start`` to ``end`` inclusive, in decreasing height
  order if ``start`` is greater than ``end``. If ``poolTypes`` is empty, the blocks contain
  only data for the Sapling, Orchard, and Ironwood pools, and omit ``CompactTxs`` with no
  such data. Otherwise they contain only data for the requested pools. A light client MUST
  verify that the server supports this filtering before setting ``poolTypes`` to a
  non-empty value.

``GetTreeState(BlockID)`` and ``GetLatestTreeState()``
  Return a ``TreeState``: the height, hash, and time of a block, and the Sapling, Orchard,
  and Ironwood note commitment tree states as of the end of that block.

``GetSubtreeRoots(GetSubtreeRootsArg)``
  Streams the roots of complete subtrees of the note commitment tree of a given pool, each
  with the hash and height of the block that completed it.

``GetTransaction(TxFilter)``
  Returns as a ``RawTransaction`` the full transaction whose txid is ``hash``. Selection by
  block and index is not supported. In the result, a ``height`` of 0 means that the
  transaction is in the mempool, a ``height`` of 0xffffffffffffffff means that it was mined
  in a block that is not in the best chain, and any other ``height`` is that of the block
  in the best chain that contains it.

``SendTransaction(RawTransaction)``
  Submits a transaction to the network. The ``SendResponse`` has ``errorCode`` 0 on
  success, and otherwise a nonzero ``errorCode`` and an ``errorMessage`` describing the
  failure.

A ``BlockID`` selects a block by height; servers are not required to support selection by
hash. The service also provides mempool queries (``GetMempoolTx`` and ``GetMempoolStream``),
transparent-address queries (``GetTaddressTransactions``, ``GetTaddressBalance``,
``GetAddressUtxos``, and their streaming variants), and server information
(``GetLightdInfo``).

Under the security model above, the light client trusts the tree states and subtree roots
provided by the proxy server, as it trusts the compact blocks. It can check their
consistency with the compact blocks it receives: the ``hash`` of a ``TreeState`` matches the
block at the same height, and the size of each note commitment tree matches the
corresponding size in the ``chainMetadata`` of that block.


Client operation
================

Light clients obtain compact blocks from one or more proxy servers, which they then
process locally to update their view of the block chain. We consider only a single proxy
server here without loss of generality.

Local processing
----------------

Given a ``CompactBlock`` at block height $\mathsf{height}$ received in height-sequential
order from a proxy server, a light client can process it in four ways:

Scanning for relevant transactions
``````````````````````````````````
For every ``CompactSaplingOutput``, and every ``CompactOrchardAction`` in ``actions`` or
``ironwoodActions``, in the ``CompactBlock``, the light client can trial-decrypt it against
a set of incoming viewing keys for the corresponding shielded protocol (Sapling, or Orchard
for both the Orchard and Ironwood pools). The procedure is that of the standard decryption
process [#protocol-saplingdecryptivk]_, as amended for Ironwood notes by ZIP 2005
[#zip-2005]_, with all constants and algorithms as defined there. Its inputs are taken from
the compact data: ``ephemeralKey`` and ``ciphertext`` give the ephemeral key and the
ciphertext, ``cmu`` or ``cmx`` gives the note commitment field, and for an Action
``nullifier`` gives the nullifier of the input note. The block height is the height of the
``CompactBlock``, and the pool is the pool of the output. The procedure deviates from the
standard one only as follows:

- The ``ciphertext`` field holds only the first 52 bytes of the note ciphertext, which
  encrypt the ``leadByte``, ``d``, ``v``, and ``rseed`` fields of the note plaintext. The
  step that decrypts the ciphertext with $\mathsf{Sym.Decrypt}$ is replaced by
  $P^{\mathsf{enc}} = \mathsf{ChaCha20.Decrypt}_{K^{\mathsf{enc}}}(\mathtt{ciphertext})$
  (defined below), which cannot fail.
- No memo is extracted, and the procedure returns the note without a memo.
- The transaction version is not available from compact data. The definition of the
  allowed lead bytes [#protocol-noteptconcept]_ does not currently depend on it.

Here $\mathsf{ChaCha20.Decrypt}_K(C)$ denotes the exclusive-or of $C$ with the ChaCha20
keystream [#RFC7539]_ generated from key $K$ with the all-zero 96-bit nonce and initial
block counter 1. This equals the first $\mathsf{length}(C)$ bytes of the plaintext that
$\mathsf{Sym.Decrypt}$ [#protocol-concretesym]_ would produce from the full ciphertext,
without verification of the authentication tag. Block 0 of the keystream is skipped because
the AEAD uses it to derive the Poly1305 key. Since the tag is not checked, the note
commitment check at the end of the procedure is what ensures the integrity of the decrypted
note plaintext (see `Output Compression`_).

Creating and updating note witnesses
````````````````````````````````````
As ``CompactBlocks`` are received in height order, and the transactions within them have
their order preserved, the ``cmu`` values in each ``CompactSaplingOutput`` can be
sequentially appended to an incremental Merkle tree of depth 32 in order to maintain a local
copy of the Sapling note commitment tree. [#protocol-merkletree]_ Likewise, the ``cmx``
values of the ``CompactOrchardAction`` entries in ``actions`` and in ``ironwoodActions``
can be appended to local copies of the Orchard and Ironwood note commitment trees, which
also have depth 32. These can then be used to create incremental witnesses for each unspent
note the light client is tracking. [#incremental-witness]_ An incremental witness updated to
height ``X`` corresponds to a Merkle path from the note to the anchor of its pool's note
commitment tree for block ``X``. [#protocol-merklepath]_

For a given pool, let ``tree`` be its note commitment tree at height ``X-1``, and
``note_witnesses`` be the incremental witnesses for unspent notes of that pool detected up
to height ``X-1``. When the ``CompactBlock`` at height ``X`` is received:

- For each ``CompactTx`` in ``CompactBlock``:

  - For each note commitment ``cm`` of that pool in that ``CompactTx``, in order (the
    ``cmu`` of each entry in ``outputs`` for Sapling, or the ``cmx`` of each entry in
    ``actions`` for Orchard or in ``ironwoodActions`` for Ironwood):

    - Append ``cm`` to ``tree``.
    - For ``witness`` in ``note_witnesses``:

      - Append ``cm`` to ``witness``.

    - If the corresponding output contains a relevant note, create an incremental witness
      from ``tree`` and append it to ``note_witnesses``.

The light client can then check that the size of ``tree`` equals the corresponding note
commitment tree size in the ``chainMetadata`` of the ``CompactBlock``.

Incremental Merkle trees cannot be rewound, so the light client should cache both the note
commitment trees and per-note incremental witnesses for recent block heights (see
`Chain reorganisations`_). Cache management is implementation-dependent, but the cache
should cover at least the maximum rollback depth of the full nodes behind the proxy server
[#protocol-blockchain]_. That depth is not fixed by consensus. ZIP 218 raises it from NU7
[#zip-0218]_, and Zebra already rolls back up to 1000 blocks. After a deeper chain
reorganisation, the light client has to rebuild its note commitment trees, for example from
a tree state obtained from the proxy server, before rescanning.

Detecting spends
````````````````

The nullifiers in ``CompactSaplingSpend`` entries (``nf``) and in ``CompactOrchardAction``
entries (``nullifier``) can be checked against known local nullifiers, for example to
ensure that a transaction has been received by the network and mined.

Block header validation
```````````````````````

*This section describes a proposed enhancement that has been only partially implemented:
currently only* ``prevHash`` *is checked, and deployed proxy servers leave the* ``header``
*field empty.*

If the ``header`` field of the ``CompactBlock`` for height ``X`` is present, the light
client can validate it in a similar way to SPV clients [#spv-clients]_. Let ``h`` be the
SHA-256d hash of ``header``, that is, of the whole block header including ``solutionSize``
and ``solution`` [#protocol-difficulty]_. The light client performs the following checks,
using the block header field names of [#protocol-blockheader]_:

- The ``header`` field is a valid block header encoding, and ``h`` equals ``hash``.
- The ``nVersion`` field is at least 4 [#protocol-blockheader]_.
- The ``hashPrevBlock`` field equals ``prevHash`` and the hash of the block at height
  ``X-1`` in the light client's chain view.
- If $\mathsf{SaplingActivationHeight} \leq \mathtt{X} < \mathsf{HeartwoodActivationHeight}$
  then ``hashFinalSaplingRoot`` is equal to the root of the Sapling note commitment tree
  after appending every ``cmu`` in the ``CompactBlock`` in order. From Heartwood activation
  this field holds ``hashLightClientRoot`` [#zip-0221]_, and from NU5 activation
  ``hashBlockCommitments`` [#zip-0244]_. Neither can be recomputed from ``CompactBlock``
  data.
- The Equihash solution is valid [#protocol-equihash]_.
- The target $\mathsf{ToTarget}(\mathsf{nBits})$ [#protocol-nbits]_ is nonzero and at most
  $\mathsf{PoWLimit}$ for the network [#protocol-constants]_.
- If the ``CompactBlocks`` for the preceding
  $\mathsf{PoWAveragingWindow} + \mathsf{PoWMedianBlockSpan}$ heights all have block
  headers (heights ``X-28`` to ``X-1`` before NU7, or ``X-113`` to ``X-1`` when ZIP 218
  [#zip-0218]_ applies at height ``X``), ``nBits`` equals
  $\mathsf{ThresholdBits}(\mathtt{X})$ as specified in [#protocol-diffadjustment]_,
  including on Testnet the minimum-difficulty rule [#zip-0205]_ [#zip-0208]_ [#zip-0218]_.
- The hash ``h`` passes the difficulty filter [#protocol-difficulty]_, that is
  $\mathsf{LEOS2IP}_{256}(\mathtt{h}) \leq \mathsf{ToTarget}(\mathsf{nBits})$ where
  $\mathsf{LEOS2IP}_{256}$ reads ``h`` as a little-endian integer.

A ``CompactBlock`` that fails any of these checks MUST be discarded. If it was received as
part of a ``GetBlockRange`` call, the call MUST be aborted.

Block header validation provides light clients with some assurance that the compact data
being sent to them is indeed from valid blocks that have been mined. The strongest-possible
assurance is achieved when all block headers are synchronised; this comes at the cost of
bandwidth and storage.

By default, ``CompactBlocks`` returned by ``GetBlockRange`` only contain ``CompactTxs`` for
transactions that have data for the Sapling, Orchard, or Ironwood pools (see
`Proxy operation`_). Thus they do not contain sufficient information to validate that the
received transaction IDs correspond to the transaction tree root in the block header. This
does not have a significant effect on light client security: light clients only directly
depend on the note commitments, nullifiers, and note ciphertexts in ``CompactBlocks``.
However, block header validation can authenticate the note commitments only before
Heartwood activation. From Heartwood activation, the header of the following block commits
to the final note commitment tree roots of a block only through the history tree
[#zip-0221]_, and checking them would require inclusion proofs that ``CompactBlocks`` do not
carry. If a txid is used in a ``GetTransaction`` call, the returned transaction SHOULD be
checked against the corresponding ``CompactTx``, in addition to verifying the transaction
signatures.

Potential extensions
````````````````````

A trivial extension (with corresponding bandwidth cost) would be to transmit empty
``CompactTxs`` corresponding to transactions that have no data for the requested pools. A
more complex extension would send the inner nodes within the transaction trees
corresponding to subtrees that contain no such transactions; this would require strictly
less bandwidth than the trivial extension. These extensions are not currently defined.


Client-server interaction
-------------------------

We can divide the typical client-server interaction into four distinct phases:

.. code:: text

    Phase   Client                Server
    =====   ============================
      A     GetLatestBlock ------------>

            <---------------- BlockID(X)

            GetTreeState(X) ----------->

            <-------------- TreeState(X)

                ===

      B     GetLatestBlock ------------>

            <---------------- BlockID(Y)

            GetBlockRange(X, Y) ------->

            <--------- CompactBlock(X)
            <--------- CompactBlock(X+1)
            <--------- CompactBlock(X+2)
                            ...
            <--------- CompactBlock(Y-1)
            <--------- CompactBlock(Y)

                ===

      C     GetTransaction(txid1) ----->

            <----- RawTransaction(txid1)

            GetTransaction(txid2) ----->

            <----- RawTransaction(txid2)

                ===

      D     GetLatestBlock ------------>

            <---------------- BlockID(Z)

            GetBlockRange(Y, Z) ------->

            <--------- CompactBlock(Y)
            <--------- CompactBlock(Y+1)
            <--------- CompactBlock(Y+2)
                            ...
            <--------- CompactBlock(Z-1)
            <--------- CompactBlock(Z)

**Phase A:** The light client starts up for the first time.

- The light client queries the server to fetch the most recent block ``X``.
- The light client fetches the note commitment tree states as of the end of block ``X``
  using ``GetTreeState``, and records the hash of block ``X``.

  - If no tree state is available, it instead sets ``X`` to the height immediately before
    Sapling activation, at which all note commitment trees are empty, and records the hash
    of that block. It then has to scan every block from Sapling activation onward.

- Shielded addresses created by the light client will not have any relevant transactions
  in this or any prior block.

**Phase B:** The light client updates its local chain view for the first time.

- The light client queries the server to fetch the most recent block ``Y``.
- It then executes a block range query to fetch every block between ``X`` (inclusive) and
  ``Y`` (inclusive).
- The block at height ``X`` is checked to ensure the received ``hash`` matches the
  light client's cached copy, and then discards it without further processing.

  - An inconsistency would imply that block ``X`` was orphaned during a chain reorg. The
    light client then rolls back as described in `Chain reorganisations`_.

- As each subsequent ``CompactBlock`` arrives, the light client:

  - Checks its ``prevHash`` as described in `Chain reorganisations`_, and validates the
    block header if it is present.
  - Scans the ``CompactBlock`` to find any relevant transactions for addresses generated
    since ``X`` was fetched (likely the first transactions involving those addresses). If
    notes are detected, it:

    - Generates incremental witnesses for the notes, and updates them going forward.
    - Scans for their nullifiers from that block onwards.

**Phase C:** The light client has detected some notes, and fetches the corresponding full
transactions (subject to the considerations in `Transaction privacy`_).

- The light client queries the server by txid for each transaction it wishes to fetch.

**Phase D:** The user has spent some notes. The light client updates its local chain view
some time later.

- The light client queries the server to fetch the most recent block ``Z``.
- It then executes a block range query to fetch every block between ``Y`` (inclusive) and
  ``Z`` (inclusive).
- The block at height ``Y`` is checked to ensure the received ``hash`` matches the
  light client's cached copy, and then discards it without further processing.

  - An inconsistency would imply that block ``Y`` was orphaned during a chain reorg. The
    light client then rolls back as described in `Chain reorganisations`_.

- As each subsequent ``CompactBlock`` arrives, the light client:

  - Checks its ``prevHash`` as described in `Chain reorganisations`_, and validates the
    block header if it is present.
  - Updates the incremental witnesses for known notes.
  - Scans for any known nullifiers. The corresponding notes are marked as spent at that
    height, and excluded from further witness updates.
  - Scans for any relevant transactions for addresses generated since ``Y`` was fetched.
    These are handled as in phase B.

Importing a pre-existing seed
`````````````````````````````
Phase A of the interaction assumes that shielded addresses created by the light client
will have never been used before. This is not a valid assumption if the light client is
being initialised with a seed that it did not generate (e.g. a previously backed-up seed).
In this case, phase A is modified as follows:

**Phase A:** The light client starts up for the first time.

- The light client sets ``X`` to the height immediately before Sapling activation, at which
  all note commitment trees are empty.

  - Shielded addresses created by any light client cannot have any relevant transactions
    prior to Sapling activation.
  - If a height is known before which the seed has no relevant transactions (a wallet
    birthday), the light client can instead set ``X`` to the height immediately before it
    and fetch the note commitment tree states for block ``X`` using ``GetTreeState``.

Chain reorganisations
`````````````````````

The light client retains the block hashes for recent heights, together with checkpoints of
its note commitment trees and incremental witnesses (see
`Creating and updating note witnesses`_).

For each ``CompactBlock`` at height ``h`` that it processes, including the first block it
processes from each requested range, the light client MUST check that ``prevHash`` equals
the hash it has recorded for height ``h-1``, if it has recorded one (a light client that
scans out of height order might not have). A mismatch means that a chain reorganisation
has orphaned the light client's block at height ``h-1``, and possibly earlier blocks. The
light client MUST NOT assume that its block at height ``h-1`` is still in the best chain.

On a mismatch, the light client MUST roll back to a height ``F`` below ``h`` whose recorded
block hash is that of the block at height ``F`` in the proxy server's best chain. How ``F``
is found is implementation-dependent; for example, the light client can rewind a fixed
number of blocks and request blocks again from there, repeating this while mismatches
persist. Rolling back discards all local blocks with height greater than ``F`` and rolls
back the following local state to height ``F``:

- All local transactions (un-mining them as necessary).
- All tracked nullifiers (unspending or discarding as necessary).
- The note commitment trees and all incremental witnesses.

If ``F`` is below the oldest cached checkpoint, the light client instead rolls back to a
lower height for which it can fetch the note commitment tree states using ``GetTreeState``
(for example its wallet birthday), and rescans from there.

Block privacy via bucketing
---------------------------

*This section describes a proposed enhancement that has not been implemented.*

The above interaction reveals to the server at the start of each synchronisation phase (B
and D) the block height which the light client had previously synchronised to. This is an
information leak under our security model (assuming network privacy). We can reduce the
information leakage by "bucketing" the start point of each synchronisation. Doing so also
enables us to handle most chain reorgs simultaneously.

Let ``⌊X⌋ = X - (X % N)`` be the value of ``X`` rounded down to some multiple of the
bucket size ``N``. The synchronisation phases from the above interaction are modified as
follows:

.. code:: text

    Phase   Client                Server
    =====   ============================
      B     GetLatestBlock ------------>

            <---------------- BlockID(Y)

            GetBlockRange(⌊X⌋, Y) ----->

            <-------- CompactBlock(⌊X⌋)
            <-------- CompactBlock(⌊X⌋+1)
            <-------- CompactBlock(⌊X⌋+2)
                            ...
            <-------- CompactBlock(Y-1)
            <-------- CompactBlock(Y)

                ===

      D     GetLatestBlock ------------>

            <---------------- BlockID(Z)

            GetBlockRange(⌊Y⌋, Z) ----->

            <-------- CompactBlock(⌊Y⌋)
            <-------- CompactBlock(⌊Y⌋+1)
                            ...
            <-------- CompactBlock(Z-1)
            <-------- CompactBlock(Z)

**Phase B:** The light client updates its local chain view for the first time.

- The light client queries the server to fetch the most recent block ``Y``.
- It then executes a block range query to fetch every block between ``⌊X⌋`` (inclusive)
  and ``Y`` (inclusive).
- Blocks between ``⌊X⌋`` and ``X`` are checked to ensure that the received ``hash``
  matches the light client's chain view for each height, and are then discarded without
  further processing.

  - In this phase the light client's chain view starts at the block ``X`` fetched in Phase
    A, so of these blocks only block ``X`` can be checked.
  - If an inconsistency is detected, the light client rolls back as described in
    `Chain reorganisations`_.

- Blocks between ``X+1`` and ``Y`` are processed as before.

**Phase D:** The user has spent some notes. The light client updates its local chain view
some time later.

- The light client queries the server to fetch the most recent block ``Z``.
- It then executes a block range query to fetch every block between ``⌊Y⌋`` (inclusive)
  and ``Z`` (inclusive).
- Blocks between ``⌊Y⌋`` and ``Y`` are checked to ensure that the received ``hash``
  matches the light client's chain view for each height, and are then discarded without
  further processing.

  - If the lowest height at which an inconsistency is detected is ``R``, and block ``R-1``
    has been checked (which requires ``R > ⌊Y⌋``), the light client sets ``Y = R-1``,
    discards all local blocks with height ``>= R``, and rolls back the following local
    state to height ``R-1``:

    - All local transactions (un-mining them as necessary).
    - All tracked nullifiers (unspending or discarding as necessary).
    - The note commitment trees and all incremental witnesses.

  - Otherwise (in particular, when ``Y`` is a multiple of ``N``, so that block ``Y`` is the
    only block checked), the light client rolls back as described in
    `Chain reorganisations`_.

- Blocks between ``Y+1`` and ``Z`` are processed as before.

Transaction privacy
-------------------

The synchronisation phases give the light client sufficient information to determine
accurate address balances, show when funds were received or spent, and spend any unspent
notes. Provided that the ranges and order of the light client's block range and tree state
requests are independent of the results of trial decryption, synchronisation leaks no
information about which transactions the light client is interested in: the server learns
only the requested heights (see `Block privacy via bucketing`_).

A light client that reorders its scanning according to the notes it detects, for example by
prioritising the blocks needed to complete the note commitment subtree that contains a newly
detected note so that the note becomes spendable sooner, reveals to the server that a
relevant note was found in a given subtree (of $2^{16}$ leaves, for the subtrees whose roots
``GetSubtreeRoots`` returns). Such a light client SHOULD either convey this reduction in
privacy to the user or mask it, for example by fixing the scan order in advance or by
interleaving decoy range requests.

If, however, the light client needs access to other components of a transaction (such as
the memo fields for received notes, or the outgoing ciphertexts in order to recover spend
information when importing a wallet seed), it will need to download the full transaction.
A ``GetTransaction`` request names the txid, and so reveals to the server a transaction that
the light client is interested in. The light client SHOULD make these requests over a
privacy-preserving network connection, such as Tor, in a way that prevents the server from
linking them to each other or to the light client's other requests (for example, by using a
separate Tor circuit for each request). A light client that downloads compact blocks over a
connection without such protection SHOULD NOT retrieve full transactions immediately upon
detecting them, but SHOULD defer retrieval so that it cannot be correlated with the compact
block requests. The light client MAY also download other transactions, such as all
transactions in the same block (whose txids are given by the ``CompactBlock`` returned by
``GetBlock``), to obscure which transactions are of interest. If it fetches full
transactions without these protections, it MUST convey to the user that this reduces their
privacy.

Other requests also reveal information to the server. A ``GetTreeState`` request for a
wallet birthday reveals that height. Transparent-address queries reveal the queried
addresses and, when several are queried together, that they belong to the same wallet. The
``exclude_txid_suffixes`` of a ``GetMempoolTx`` request reveal which mempool transactions
the light client already has, and ``SendTransaction`` reveals that the light client is the
source of the submitted transaction. A light client should take this into account, for
example by making such requests over privacy-preserving connections that the server cannot
link to each other.
